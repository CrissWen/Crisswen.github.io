# Виправлення безпеки — 12 листопада 2026

Міграція `migrations/202611120001_security.sql` призначена для наданої схеми TrueBunker.
Вона змінює права доступу й додає серверні таблиці учасників, результатів та сповіщень.
Існуючі кімнати, картки та історія не видаляються.

## Застосування

1. Збережіть резервну копію схеми та даних Supabase. Перевірте міграцію на окремому проєкті, якщо схема відрізняється від наданої під час аудиту.
2. У період без активних ігор відкрийте **SQL Editor → New query**, вставте **весь** файл міграції та виконайте як `postgres`. Файл містить `BEGIN` / `COMMIT`: помилка скасує зміни транзакції; після помилки не виконуйте решту файлу окремо.
3. Одразу опублікуйте відповідну версію frontend з цього репозиторію та перезавантажте відкриті вкладки. Старий frontend несумісний з новими обмеженнями читання кімнат. Без застосування SQL локальні зміни frontend ще не закривають доступ до бази.
4. Виконайте `verify-security.sql`. У всіх рядках `ok` має бути `true`.
5. Перевірте двома звичайними акаунтами: створення кімнати, вхід за кодом, старт, власні картки, відкриття характеристик, голосування, передачу ведучого, фінал та експорт реплею. Для соло-перевірки використовуйте справжнього адміністратора з таблиці `admins`.

Нові коди кімнат мають 8 випадкових символів із криптографічного генератора. Код є запрошенням: знання коду дозволяє зареєстрованому користувачу зайти гравцем або глядачем. Відкритого переліку чужих кімнат більше немає.

Учасникам старих незавершених кімнат потрібно повторно відкрити гру: старий JSON-список учасників не вважається доказом особистого входу для статистики. Глядачі не потрапляють у статистику. Уже збережена історія залишається; міграція не намагається автоматично виправляти можливі старі підроблені результати.

## Межі доступу

- `get_room_view` повертає власні картки, відкриті чужі картки та публічний стан. Ведучий отримує повний стан для керування грою; після фіналу зареєстрованим учасникам доступні всі картки, як і раніше.
- Realtime публікує лише `room_events(room_code, version)`. Повний рядок `rooms` вилучено з публікації. Після сповіщення клієнт викликає захищений RPC; раз на 5 секунд перевіряє стан для відновлення після втрати сповіщень.
- Особистий пак читає автор та поточний ведучий кімнати, у якій його обрано. Базовий пак можна читати без авторизації.
- Статистика записується лише для підтверджених учасників, ведучим завершеної гри, з блокуванням від повторного запису. Поля статистики й таблиця історії закриті для прямого запису клієнтом.
- Ведучий залишається довіреним організатором: він може вручну змінювати характеристики, місткість та вибування. Ця модель не забезпечує незалежного від ведучого підтвердження чесності результату.
- Обслуговування `handle_room_lifecycle` доступне власнику функції та `service_role`; наявне cron-завдання від `postgres` продовжує працювати. Не додавайте `service_role` до frontend.
- Допоміжні HTML-інструменти перевіряють реальне членство в `admins`, без dev/localStorage/metadata-обходів. Самі статичні HTML/JS-файли на GitHub Pages залишаються публічними ресурсами.

## Перевірки

```powershell
npm ci --prefix tests/security
npm test --prefix tests/security
node --test tests/auth-profile/*.test.mjs tests/game/*.test.mjs tests/pack-editor/*.test.mjs tests/ui/*.test.mjs tests/audio/*.test.mjs
```

Нові тести виконують SQL у локальному PostgreSQL через PGlite; зовнішню Supabase-базу вони не змінюють. Перевіряються ролі `anon` / `authenticated`, RLS, ACL, приватність карток, статистика, журнали, передача ведучого, публікація Realtime і повторне застосування міграції.

У початковій версії репозиторію вже падає тест `tests/ui/info-pages.test.mjs` про згадку таймера «60 секунд» у правилах. Це відтворено на незміненому `HEAD`; виправлення безпеки не змінюють тексти правил.
